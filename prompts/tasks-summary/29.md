# Task 29 - Multi-Target Announcements, Term Filtering, Assessment Archiving, and AI Removal

Summary of the implementation for `prompts/tasks-assignment/29.md`: announcements can now target
several subjects at once, the learning-materials page gained an academic-term filter, assessments
can be archived in batches without touching a single student score, the assessment sidebar item
became a dropdown, and the Groq AI assistant was removed from the platform entirely.

---

## Plain-language summary

**Announcements** are no longer limited to one target. The Target field is a multi-select, so one
announcement can go to several subjects (and therefore several sections) at once. Opening an
existing announcement for editing shows every target that was previously chosen, already selected.
The global switch still overrides everything and sends to all enrolled students. A student enrolled
in two of the targeted subjects sees the announcement once and gets one notification, not two.

**Learning materials** gained a Term filter next to the existing subject, section and status
filters. Materials have no term of their own — they inherit it through their subject's section — so
the filter walks that chain. Inactive terms stay hidden, as Task 26 intended; the filter narrows
within the active ones.

**Assessments** can now be archived. Tick any number of rows on the assessments page and press
"Archive selected", the same batch-selection pattern the question bank uses. Archived assessments
move to a dedicated **Archived Assessments** page where they can be restored in a batch. The
archived page shows a "N score(s) retained" column for each row, so the score preservation is
visible rather than merely promised.

**Archiving never touches scores.** Archiving is a flag on the assessment, not a delete. Every
score row, its link to the assessment, the score matrix, the exports and the student's own score
history keep working exactly as before. Archived assessments simply drop out of the active lists
(educator index, student assessment list, dashboards, calendar, monitoring, question-bank filters)
and can no longer be opened or taken by a student.

**Assessments in the sidebar** is now a dropdown with **Assessments** and **Archived Assessments**,
matching the existing Question Bank and Scores menus.

**The AI assistant is gone.** The topbar button, the drawer, the Groq client, the budget tracker,
the guardrails, the retrieval tools, the routes, the rate limiter, the config block, the log channel
and the environment keys were all removed. Nothing else in the app depended on it.

---

## Why archiving is a flag, not a soft delete

The question bank and archived scores both archive via Laravel soft deletes, and copying that here
was the obvious move — but it would have broken the task's binding constraint. `Score::visibleTo`
filters through `whereHas('assessment.academicTerm', ...)`, and the score matrix, the export service
and the student score pages all resolve the assessment relation. A soft-delete global scope on
`Assessment` would have silently dropped every archived assessment out of those queries, i.e. hidden
student score history, unless every one of them was found and given `withTrashed()`. A boolean flag
inverts the failure mode: the worst a missed filter can do is show a stale row in a list.

The batch-selection **workflow** still follows the question-bank pattern exactly, which is what the
task asked for.

## What changed

### Multi-subject announcements

- `database/migrations/2026_07_28_000002_create_announcement_subject_table.php` — new
  `tbl_announcement_subject` pivot, backfilled from the old `tbl_announcements.subject_id`, which is
  then dropped along with its index.
- `app/Models/Announcement.php` — `subject()` belongs-to became `subjects()` belongs-to-many;
  `scopeVisibleTo` rewritten: the educator branch uses `whereDoesntHave('subjects')` /
  `whereHas('subjects.section.academicTerm')`, the student branch matches enrollment against the
  pivot with an `EXISTS` (not a join) so a doubly-enrolled student sees one row.
- `app/Http/Requests/StoreAnnouncementRequest.php` — `subject_id` → `subject_ids[]`, each id still
  re-checked against the educator's own subjects. `UpdateAnnouncementRequest` was a copy of its
  parent's rules and is now an empty subclass.
- `app/Http/Controllers/Educator/AnnouncementController.php` — sync targets on store/update, load
  them on edit, notify the union of enrolled students once each, and sort the Target column by the
  alphabetically-first target via a correlated subquery (a join would duplicate rows).
- Views: `educator/announcements/_form.blade.php` — the target picker is the KTUI **enhanced tags**
  select (`data-kt-select` / `-multiple` / `-tags` / `-enable-search`), so each chosen subject
  becomes a removable tag with a searchable dropdown, matching the enrollment form's multi-selects.
  Also `educator/announcements/index`,
  `student/announcements/_card`, `student/announcements/_timeline`.
- `app/Http/Controllers/Student/AnnouncementController.php` — eager load `subjects`.
- `resources/views/partials/_modal-loader.blade.php` — the global-switch handler drove
  `select.disabled`, which does nothing visible once KTSelect hides the native element behind its
  own wrapper (verified in-browser: the wrapper kept `pointer-events: auto` and gained no
  `disabled` class). It now calls `KTSelect.getInstance(el).disable()/.enable()` as well.

### Learning-materials term filter

- `app/Http/Controllers/Educator/MaterialController.php` — `term` filter closure walking
  `subject.section.academic_term_id`, plus `$filterTerms`.
- `resources/views/educator/materials/index.blade.php` — one `data-filter="term"` select; the shared
  data-table component wires it up with no extra JS.

### Assessment archiving

- `database/migrations/2026_07_28_000001_add_is_archived_to_tbl_assessments.php` — indexed boolean.
- `app/Models/Assessment.php` — `is_archived` fillable + cast, `scopeNotArchived()` /
  `scopeOnlyArchived()`. `scopeVisibleTo` was deliberately left alone.
- `app/Http/Controllers/Educator/AssessmentController.php` — `archive()`, `archived()`,
  `restoreArchived()`, sharing a `setArchived()` helper that re-authorizes each row with the
  existing `update` policy inside a transaction. `destroy()` is unchanged.
- `routes/web.php` — three routes declared before `Route::resource('assessments')`, which is now
  `->whereUuid('assessment')` so the literal segments are not swallowed by the uuid route binding.
- `->notArchived()` applied to the active listings: educator assessment index and its code filter,
  student assessment list and term dropdown, educator dashboard (pending / calendar / next /
  heatmap), student dashboard, admin dashboard calendar, shared calendar, live monitoring, and the
  question-bank assessment filter.
- `app/Http/Controllers/Student/QuizController.php` — `authorizeQuizAccess()` refuses an archived
  assessment, so it cannot be reached by direct URL either.
- Untouched on purpose: `Educator\ScoreController`, `ScoreExportService`, `Student\ScoreController`,
  `Score::visibleTo` — these are the score-history paths.
- Views: `educator/assessments/index.blade.php` (row checkboxes + bulk archive toolbar),
  new `educator/assessments/archived.blade.php`.

### Exemption and special-access messages render as alerts (follow-up)

Exemption and special-access messages still land in the student's private thread, but they were
rendering as an ordinary blue chat bubble, which read as if the educator had typed them. They are
now tagged as system messages and rendered with the KTUI **alert** component instead.

- `database/migrations/2026_07_28_000003_add_kind_to_tbl_conversation_messages.php` — nullable
  `kind` column. `NULL` is an ordinary typed message.
- `app/Models/ConversationMessage.php` — `ALERT_KINDS` maps each kind to a variant, icon and
  heading (`assessment_exempted` → warning / information-2 / "Assessment exemption";
  `assessment_access_granted` → info / time / "Special access granted"), plus `isAlert()` and
  `alertStyle()`.
- `app/Services/ConversationService.php` — `sendMessage()` takes an optional `$kind`.
- `app/Http/Controllers/Educator/AssessmentController.php` — the two sends pass their kind.
- `resources/views/layouts/partials/_conversation_thread.blade.php` — an alert-kind message renders
  as `kt-alert kt-alert-light kt-alert-{variant} kt-alert-outline` spanning the thread width, with
  an icon, a heading and the message as the description, plus the usual timestamp and read receipt.
  No avatar, no bubble tail, no edit/delete buttons. Ordinary messages are unchanged.
- `app/Policies/ConversationMessagePolicy.php` — `update`/`delete` refuse an alert message. It is a
  record of an action, so its author cannot rewrite or retract it; the buttons being hidden in the
  view is not the enforcement.

### Sidebar

- `resources/views/educator/layout.blade.php` — Assessments converted to the existing dropdown
  shape with Assessments / Archived Assessments children.

### AI removal

Deleted: `Educator/AssistantController`, `AssistantMessageRequest`, the whole `app/Services/Ai/`
directory (`AiAudit`, `AssistantGuard`, `AssistantService`, `EducatorDataTools`, `GroqBudget`,
`GroqClient`, `GroqUnavailableException`), `layouts/partials/_assistant_drawer.blade.php`, and three
test files (`AssistantTest`, `AssistantAlertCoverageTest`, `GroqBudgetTest`).

Edited: `routes/web.php` (import + two routes), `_demo1_topbar_icons.blade.php` (the trailing
educator include only — the notifications and chat drawer above it are untouched),
`FortifyServiceProvider` (the `assistant` rate limiter), `config/services.php` (`groq` block),
`config/logging.php` (`ai` channel), `.env.example` (`GROQ_*` block).

No migrations, tables, composer packages or npm packages had been added for the AI feature, so there
was nothing to undo there. `prompts/tasks-assignment/28.md` was kept as build history.

**Manual follow-up:** remove `GROQ_API_KEY`, `GROQ_MODEL`, `GROQ_BASE_URL`, `GROQ_RPM/RPD/TPM/TPD`
and `AI_LOG_DAYS` from the real `.env`, and revoke the Groq API key at the provider. Stale
`storage/logs/ai-*.log` files can be deleted.
