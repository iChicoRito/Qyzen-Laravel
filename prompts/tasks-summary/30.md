# Task 30 - Exemption and Special-Access Alerts

Summary of the implementation for `prompts/tasks-assignment/30.md`: exemption and special-access
messages now render as KTUI light alerts in the correct variants, the generated wording was
tightened, and every historical message was retagged so it renders as an alert too.

> Note: the previous contents of this file were a verbatim copy of the assignment, not a summary.
> It was replaced.

---

## Plain-language summary

Exemption and special-access messages already rendered as KTUI light alerts (built during Task 29),
but in the wrong colours. They now follow the spec: **exemption is a destructive alert** (something
was taken away) and **special access is a success alert** (something was granted), each with a
matching icon.

The generated sentences were also shortened. They used to read "You have been exempted from
**assessment** Quiz #1", which reads awkwardly next to a code like "Quiz #1" that already names the
assessment. The word is gone from both messages. And when no reason was recorded, the exemption
message used to end with a dangling `Reason:` and nothing after it; the label is now dropped
entirely in that case.

Finally, every exemption and special-access message sent *before* the alert work existed was still
rendering as a plain chat bubble — 112 of the 113 in the database. A backfill migration retagged
them, so students see a consistent presentation across their whole history.

## What changed

  `assessment_exempted` → `destructive` / `ki-shield-cross`, `assessment_access_granted` →
  `success` / `ki-shield-tick`. (Was `warning` / `info`.) The thread partial already renders
  `kt-alert kt-alert-light kt-alert-{variant} kt-alert-outline` from this map, so no view change
  was needed. Both `.kt-alert-light.kt-alert-destructive` and `.kt-alert-light.kt-alert-success`
  were confirmed present in the compiled Metronic stylesheet before use.
- `app/Http/Controllers/Educator/AssessmentController.php` —
  - exemption: `'You have been exempted from '.$code` (dropped "assessment"), and the
    `' Reason: '.$reason` clause is appended only when a trimmed reason is non-empty.
  - special access: `'You have been granted special access to '.$code` (dropped "assessment").
  - the notification `metadata.reason` is now `null` rather than an empty string when blank.
- `database/migrations/2026_07_29_000001_backfill_kind_on_system_conversation_messages.php` —
  retags untagged messages by their generated opening phrase. Matches both the pre- and
  post-Task-30 wording, skips rows that already carry a kind, and skips deleted messages.

## The duplicate-message item was not implemented — deliberately

The assignment's headline defect is a message that reads:

```
You have been exempted from assessment Quiz #1. Reason: You have been exempted from assessment
Quiz #1. Reason: <the actual reason>
```

This could not be reproduced, and the evidence says it is already fixed:

- There is exactly one place that builds this string (`toggleExemption`), and it concatenates the
  assessment code with `$data['reason']` — it never concatenates a previously formatted message.
- The reason textarea in `educator/assessments/exemptions.blade.php` is not pre-filled, so a stored
  message cannot be round-tripped back into the reason field.
- Against the live database: **0** messages contain a doubled statement or a doubled `Reason:`
  label, and **0** exemption rows have a reason that embeds the full message.

The most likely original cause is the bug Task 24 fixed — re-saving an exemption set used to
overwrite the stored reason, so a re-save could fold formatted text back into the reason column.
That guard (`$newlyExemptedIds->contains($studentId)` before writing `reason`) is already in place.

Writing speculative de-duplication code against a defect that no longer exists would add a
permanent workaround for a transient bug, so the wording fix was implemented and the de-duplication
was not. If a duplicated message does resurface, the reproduction steps are the missing input.

Also noted while checking the data: exemption row #171 has
`reason = 'http://localhost:8001/educator/assessments'`, which went to a student verbatim. That is
a paste accident rather than a bug, but the reason field validates only `max:255`.

## Tests

`php artisan test` — **363 passed, 1734 assertions.**

- `tests/Feature/PrivateMessagingTest.php`
  - `test_exemption_alerts_use_the_destructive_variant` — asserts the destructive classes, absence
    of the old `kt-alert-warning`, that a reasonless message renders with no dangling `Reason:`,
    that `Reason: Medical absence` appears exactly once, and that `exempted from assessment` is
    gone.
  - `test_backfill_retags_legacy_system_messages_and_leaves_typed_ones_alone` — runs the migration
    against old-wording and new-wording rows and asserts a student's own sentence that merely
    mentions an exemption is left untagged.
  - `test_system_messages_render_as_a_kt_alert_and_are_immutable` — updated to the success variant.
- `tests/Feature/Educator/EducatorFeaturesTest.php` — the exemption and special-access assertions
  now pin the exact new wording.

**Not covered by a test:** an exemption created with no reason. `StoreAssessment`-side validation
makes `reason` required whenever a genuinely new exemption is in the payload, so that path is
unreachable through the controller today; only legacy rows have a null reason. The rendering of
such a message *is* covered above.
