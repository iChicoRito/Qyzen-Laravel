# Task 31 - Fix 404 Errors Across Educator Pages After Term Deactivation

Summary of the implementation for `prompts/tasks-assignment/31.md`: the active-term test was moved
out of the educator half of every `visibleTo()` scope, so deactivating a term no longer turns its
existing records into 404s for the educator who owns them. Student behaviour is deliberately
unchanged.

---

## Plain-language summary

When PRELIM was marked inactive and MIDTERM took over, every educator page stopped being able to
find PRELIM's data. Previewing a class at `/educator/scores` returned **404 Not Found** even though
the scores were still in the database, and the PRELIM class rows vanished from the index entirely.

The cause was a category error rather than a missing feature. The check "is this term still active?"
had been written into `visibleTo()` — the scope that answers "does this user own / have access to
this record?". That scope is used both to build lists *and* to resolve a single record before a
policy check. So the moment a term went inactive, its records stopped resolving at all, and
`findOrFail()` correctly reported them as missing.

Ownership does not expire when a term rolls over. The two questions are now separated: `visibleTo()`
answers ownership only, and the active-term filter is kept where it genuinely describes a *current*
workflow — the student's operational lists, and the term dropdown when creating something new.

A second, smaller failure had the same root: `classContext()` in the scores controller resolved the
requested term with `AcademicTerm::where('is_active', true)->findOrFail(...)`, which is the literal
404 the user saw when clicking Preview.

Per the scope decision taken before implementation, **students were left exactly as they were** —
they still see only current-term subjects, assessments, materials and scores. See the open item at
the bottom, which matters for the live database.

## What changed

### The eight `visibleTo()` scopes

In each model the `whereHas(...academicTerm, is_active = true)` line sat *above* the role branch, so
it applied to admins-excluded, educators and students alike. It was moved **into the student branch
only**; the educator branch is now a pure ownership predicate.

- `app/Models/Assessment.php` — via `academicTerm`
- `app/Models/Score.php` — via `assessment.academicTerm`
- `app/Models/Section.php` — via `academicTerm`
- `app/Models/Subject.php` — via `section.academicTerm`
- `app/Models/Enrolled.php` — via `subject.section.academicTerm`
- `app/Models/Quiz.php` — via `subject.section.academicTerm`
- `app/Models/LearningMaterial.php` — via `subject.section.academicTerm`
- `app/Models/Announcement.php` — the educator-side `whereDoesntHave('subjects')
  ->orWhereHas('subjects.section.academicTerm', ...)` wrapper was dropped entirely; the student
  branch (both the global-announcement join on `tbl_academic_term.is_active` and the
  subject-targeted `whereHas`) is untouched.

No call site needed changing. All ~130 `visibleTo()` uses and every Policy that delegates to it
(`ScorePolicy`, `AssessmentPolicy`, `SubjectPolicy`, `SectionPolicy`, `QuizPolicy`,
`LearningMaterialPolicy`, `AnnouncementPolicy`) inherited the fix.

### Record resolution

- `app/Http/Controllers/Educator/ScoreController.php` — `classContext()` now resolves the term by
  identity: `AcademicTerm::findOrFail($data['term'])`. A nonexistent id still 404s, and a term the
  educator has no data in still yields an empty class, because the assessment lookup below it is
  ownership-scoped.

### Term filter dropdowns

Both were hardcoded to active terms, which made historical rows unfilterable even once they were
visible. They now derive from the educator's own records — the same pattern
`Student/QuizController` already used.

- `app/Http/Controllers/Educator/ScoreController.php` — terms drawn from
  `Assessment::visibleTo($user)->select('term')`.
- `app/Http/Controllers/Educator/MaterialController.php` — terms drawn from
  `Section::visibleTo($user)->select('academic_term_id')`.

`Student/ScoreController.php:97` was left alone: students are out of scope, and its `is_active`
clause is redundant there anyway since the surrounding `whereIn` is already student-scoped.

### Edit forms — the same root cause, one step downstream

`UpdateAssessmentRequest` and `UpdateSectionRequest` extend their Store counterparts, which require
`Rule::exists('tbl_academic_term', 'id')->where('is_active', true)`. So an educator could open an
old PRELIM assessment but not save it — the term it already carried failed validation. Not a 404,
but the same conflation of "current term" with "valid term".

The term rule was extracted into a `protected function termRule()` on each Store request and
overridden on each Update request to accept **an active term OR the one the record already has**.
Picking a *different* inactive term still fails. Creating still requires an active term.

- `app/Http/Requests/StoreAssessmentRequest.php` / `UpdateAssessmentRequest.php` — the Update
  override reads `$this->route('assessment')?->term`. This also covers `storeDuplicate`, which binds
  the source assessment.
- `app/Http/Requests/StoreSectionRequest.php` / `UpdateSectionRequest.php` — the Update override
  reads `$this->route('section')->terms->pluck('id')`.

Matching option lists so the form can actually show the term it now accepts:

- `app/Http/Controllers/Educator/AssessmentController.php` — `formData()` takes an optional
  `?Assessment $assessment`; `edit()` and `duplicate()` pass it, `create()` does not.
- `app/Http/Controllers/Educator/SectionController.php` — `edit()` adds the section's own terms;
  `create()` unchanged.

## Tests

`composer test` — **364 passed, 1746 assertions.**

Two existing tests encoded the old behaviour as if it were intended, and were inverted:

- `tests/Feature/AuthorizationMatrixTest.php` —
  `test_inactive_term_hides_related_resources_from_educators_and_students` became
  `..._from_students_but_not_educators`. Every educator assertion flipped to `assertTrue`; all
  student assertions stay `assertFalse` and the two admin assertions stay `assertTrue`. Three new
  assertions against `eduB` confirm that ownership is still the gate — another educator's
  inactive-term records remain invisible.
- `tests/Feature/Educator/EducatorFeaturesTest.php` —
  `test_inactive_term_blocks_educator_score_detail_route` became
  `test_inactive_term_still_allows_educator_score_detail_route` (`assertForbidden` → `assertOk`).

One new regression test covers the reported scenario end to end:

- `test_educator_can_still_open_score_matrix_after_term_is_deactivated` — builds a PRELIM class with
  an enrolment and a recorded attempt, deactivates the term, then asserts the class row still lists
  on `/educator/scores`, the matrix modal renders the attempt, per-student detail resolves, and a
  nonexistent term id still returns 404.

`vendor/bin/pint` was run on the four models whose chaining indentation changed. The pre-existing
Pint failures in `ScoreController.php` were confirmed to predate this task (checked by stashing the
file) and were left alone.

## Open item — students currently see nothing

Not caused by this task, but surfaced by it and worth acting on.

All 10 sections in the live database sit on PRELIM; MIDTERM has **zero**. Because the student side
of `visibleTo()` still requires an active term — the scope decision taken for this task — a sampled
enrolled student (id 1570) with 1 enrolment and 3 recorded scores currently resolves to:

```
subjects=0  assessments=0  scores=0  materials=0
```

This was true before the fix as well. There are two ways out, and it is a product decision rather
than a bug fix:

1. Move the sections onto MIDTERM (or add MIDTERM sections), which is what the term rollover
   presumably intended.
2. Apply the same ownership/workflow split to the student branch — at minimum letting a student read
   their own historical scores from an inactive term, so the educator and the student who took the
   assessment do not disagree about whether it exists.
