# Task 31 - Inactive Terms Hide Their Records Without Erroring

Summary of the implementation for `prompts/tasks-assignment/31.md`.

Deactivating an academic term now hides everything filed under it, consistently, and without any
error pages. The 404 that prompted the task is gone — not by making the hidden data visible, but by
making every screen agree on what "hidden" means.

> Note: this file previously described the opposite resolution — keeping inactive-term data visible
> to the owning educator. That was implemented, then reversed on the product decision recorded
> below. The current behaviour is what is documented here.

---

## Plain-language summary

### What was actually broken

`/educator/scores` listed a class and then returned **404 Not Found** when you clicked Preview on it.

The reason was that an assessment sits under *two* different terms and the app tested a different
one on each screen:

- an assessment has its own `term` column — the term the educator picked when creating it;
- it also hangs off a **section**, which has its own `academic_term_id`.

Those can disagree, and in the live data they did: four assessments were filed under **MIDTERM**
while the sections they belong to were still on **PRELIM**. So after PRELIM was deactivated:

- the scores index tested `assessment.term` → MIDTERM → active → **the row appeared**;
- the preview tested `section.academicTerm` → PRELIM → inactive → **404**.

Same screen, two answers. That inconsistency is the bug.

### What it does now

An assessment is only visible when **both** of its terms are active. Every list, lookup and policy
now asks that one question, so a row can never appear in a place that will then refuse to open it.

Deactivating a term hides its sections, subjects, assessments, scores, questions, materials,
enrolments and targeted announcements — from educators and students alike. The rows are not
deleted; they come back the moment an administrator reactivates the term.

And nothing errors. A stale tab or bookmark pointing at one of your own now-hidden records
redirects to the educator dashboard with a notice instead of showing a 403 or 404 page. The class
preview, which loads inside a modal, renders a small "this class is in an inactive term" panel
rather than injecting an error page into the modal body.

Two things deliberately still error, because softening them would be wrong:

- **Another educator's record** still returns 403/404. Turning that into a friendly notice would
  confirm the record exists to someone who should not know.
- **A genuinely unknown id** still returns 404.

## What changed

### One consistent definition of "this record's term"

- `app/Models/Concerns/HasAcademicTerm.php` *(new)* — a `scopeInActiveTerm()` built from a
  `$academicTermPath` relation path, plus `termIsActive()` for a single row. Used by
  `Section` (`academicTerm`), `Subject` (`section.academicTerm`), `Enrolled`, `Quiz` and
  `LearningMaterial` (`subject.section.academicTerm`).
- `app/Models/Assessment.php` — overrides `scopeInActiveTerm()` to require **both** its own
  `academicTerm` and its `section.academicTerm`. This is the fix for the reported 404.
- `app/Models/Score.php` — overrides it to delegate to its assessment, so a score inherits both
  term tests rather than naming a path of its own.
- `app/Models/Announcement.php` — overrides it: a global announcement targets no subject and so has
  no term, and is never hidden; a targeted one survives while any of its subjects is in a live term.

Every `scopeVisibleTo()` now calls `inActiveTerm()` instead of hand-writing its own `whereHas`, so
the eight models can no longer drift apart the way `Assessment` and `Subject` had.

`termIsActive()` runs `withoutGlobalScopes()`. It asks one narrow question about one row, and must
not answer "no" merely because the row is soft-deleted — `Score` and `Quiz` both soft-delete, and an
archived score in a live term has to stay restorable. (This was caught by an existing test.)

### No error pages

- `app/Http/Middleware/RedirectInactiveTermRecords.php` *(new)*, registered on the educator route
  group in `routes/web.php`. Before the controller runs, it inspects the route's bound models; if
  one belongs to this educator and its term is inactive, it redirects to the dashboard with a
  notice (or returns 409 for JSON). Someone else's record is left alone so it still produces the
  normal 403/404.

  This is middleware rather than an exception handler because the policies are inconsistent:
  `ScorePolicy` routes through `visibleTo()` and throws, while `AssessmentPolicy::update()` compares
  `educator_id` directly and would have rendered the page. Middleware closes both, before either
  gets a say, and covers routes added later for free.

- `app/Http/Controllers/Educator/ScoreController.php` — `classContext()` returns `null` instead of
  404ing when the class is the educator's own but term-hidden; `matrix()` and `studentDetail()`
  then render `resources/views/educator/scores/inactive-term.blade.php` *(new)*. This has to be a
  fragment, not a redirect: the modal loader injects the response body verbatim, so a redirect
  would drop a whole page inside the modal. Unknown or foreign ids still `abort(404)`.

### Reverted from the first attempt

The first implementation made inactive-term data *visible* to its owning educator, which required
widening the term dropdowns and the edit-form validation. All of that was reverted once the
behaviour was reversed — `StoreAssessmentRequest`, `StoreSectionRequest`, `UpdateAssessmentRequest`,
`UpdateSectionRequest`, `AssessmentController::formData()`, `SectionController::edit()` and the two
term filter lists are back to active-terms-only. Creating and editing were already impossible for a
hidden record, so the widening was dead code.

## Tests

`composer test` — **365 passed, 1755 assertions.**

- `tests/Feature/AuthorizationMatrixTest.php` —
  `test_inactive_term_hides_related_resources_from_educators_and_students` asserts all eight scopes
  hide the records from both roles, that admin still sees them, and that the rows still exist.
- `tests/Feature/Educator/EducatorFeaturesTest.php`
  - `test_inactive_term_redirects_educator_instead_of_erroring` — a stale link to the educator's own
    hidden score and assessment redirects with a flash notice, while educator B still gets 403.
  - `test_assessment_in_active_term_on_inactive_term_section_is_hidden_everywhere` — the regression
    test for the reported bug. Builds the exact shape (assessment on a live term, section on a dead
    one), then asserts it is not listed, that the preview and per-student detail render the notice
    rather than 404, that an unknown term id still 404s, and that educator B still 404s.
  - `test_archived_score_in_an_active_term_is_not_treated_as_term_hidden` — pins the soft-delete
    case above, which broke `test_deleted_scores_are_owner_scoped_and_restorable` during development.

## What to do next with the data

The app is now consistent, but the underlying data still needs a decision: **every section is on
PRELIM and MIDTERM has none**, so educators and students both currently see an empty app. Two ways
forward, neither of which is a code change:

1. Create MIDTERM sections, or move the existing sections onto MIDTERM, so the term rollover
   actually carries the classes with it. The four assessments already filed under MIDTERM suggest
   this is what was intended.
2. Reactivate PRELIM until that migration is done.

Worth noting for whoever does it: nothing currently stops an educator from filing an assessment
under a term that its section does not belong to. That mismatch is what made the bug possible, and
the app now hides such an assessment rather than half-showing it — but rejecting the combination at
creation time would prevent it being created at all.
