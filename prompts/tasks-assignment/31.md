# Objective

## Investigate and Fix 404 Errors Across Educator Pages After Term Deactivation

---

## Role

You are a software developer responsible for debugging and correcting term-related data access and routing issues across the educator-facing modules.

---

## Description

Investigate why educator pages return a **404 Not Found** error after a term containing existing student data is marked inactive from the admin side. The issue occurs when previewing student scores at `/educator/scores` and is also present across other educator modules and pages. Review all educator-facing pages to identify any logic, queries, routes, or data dependencies that incorrectly restrict access to records associated with inactive terms. Implement a fix that preserves access to historical data from inactive terms while ensuring the current active term continues to function correctly.

---

## Primary Objective

Scan all educator-facing pages, identify the cause of the term-related 404 errors, and fix the system so educators can access existing data from both active and inactive terms.

---

## Secondary Objectives

* Investigate the `/educator/scores` page and determine why previewing student scores returns a 404 error after a term is deactivated.
* Review the remaining educator modules and pages for the same active-term dependency or failure condition.
* Correct any routing, authorization, query-filtering, record-resolution, or data-loading logic that treats inactive-term records as nonexistent.
* Ensure that changing the active term from **PRELIM** to **MIDTERM** does not make existing PRELIM data inaccessible.

---

## Success Criteria

* `/educator/scores` no longer returns a 404 error when accessing valid student score data associated with an inactive term.
* Existing PRELIM data remains accessible after PRELIM is marked inactive and MIDTERM becomes active.
* Educator modules and pages continue to load valid historical records regardless of whether their associated term is active or inactive.
* Active-term workflows continue to use MIDTERM correctly.
* Invalid or genuinely nonexistent records still return the appropriate 404 response.
* All educator-facing pages are reviewed for the same issue, and every affected module is corrected.

---

## Context & Dependencies

* Terms are managed from the admin side and can be marked active or inactive.
* PRELIM previously contained existing student data and was later marked inactive when MIDTERM became the active term.
* After PRELIM was deactivated, educator-facing pages began returning **404 Not Found** when attempting to access existing data.
* The issue is visible on `/educator/scores` when previewing student scores and also affects other educator modules and pages.
* The fix must account for the distinction between selecting the current active term and retrieving valid historical data associated with inactive terms.

---

## Stakeholders

* **Administrators:** Manage the active and inactive status of academic terms.
* **Educators:** View student scores and access data across educator-facing modules.
* **Students:** Have score and academic records associated with specific terms.

---

## Supporting Tasks

### Reproduce and Diagnose the Issue

* Reproduce the scenario by using PRELIM with existing data, marking PRELIM inactive, activating MIDTERM, and accessing the affected educator pages.
* Trace the request flow for `/educator/scores`, including routes, controllers, middleware, services, model bindings, policies, and database queries.
* Determine whether the 404 response is caused by active-term filtering, route-model binding, missing relationships, authorization logic, or explicit record-not-found handling.
* Identify every educator page that relies on the same term-resolution logic.

### Review Educator Modules

* Scan all educator routes, controllers, components, services, and data queries for conditions that require a term to be active before its records can be retrieved.
* Check whether historical records are being filtered out through conditions equivalent to `active = true`, active-term scopes, or current-term-only relationships.
* Review shared helpers, middleware, repositories, and model scopes used by multiple educator modules.
* Verify that educator pages distinguish between the active term used for current operations and the term associated with an existing historical record.

### Implement the Fix

* Update the affected logic so valid records remain retrievable when their associated term is inactive.
* Retain active-term filtering only where the workflow specifically requires the current active term.
* Prevent valid historical records from being converted into 404 responses solely because their term is inactive.
* Apply the correction consistently across every affected educator module.

### Validate the Correction

* Test educator access to MIDTERM data while MIDTERM is active.
* Test educator access to existing PRELIM data while PRELIM is inactive.
* Confirm that switching active terms does not remove access to previously stored records.
* Verify that nonexistent records still return a legitimate 404 response.
* Check all educator pages for regressions after the shared term-handling logic is updated.

---

## Detailed Breakdown

### Current Failure Scenario

PRELIM contains existing student data. From the admin side, PRELIM is marked inactive because MIDTERM is now the active term. After this change, attempting to preview student scores through `/educator/scores` returns **404 Not Found**, even though the requested records already exist. The same behavior appears in other educator-facing modules and pages.

### Required Term-Handling Behavior

The active term should determine the default term used for current educator workflows. However, marking a term inactive must not cause existing records associated with that term to be treated as missing. Educators must still be able to retrieve and view valid historical data from PRELIM after MIDTERM becomes active.

### Investigation Scope

The investigation must cover all educator-facing pages rather than only `/educator/scores`. Shared term filters, global scopes, model bindings, middleware, authorization checks, and reusable query logic must be examined because the same implementation may be causing the 404 response across multiple modules.

### Expected Fix

Correct the underlying term-resolution and record-retrieval logic so that active-term status is applied only when selecting the current operational term. Existing records must be resolved according to their actual associated term, regardless of whether that term is currently active or inactive.
