# Objective

## Redesign Student Exemption and Special-Access Notifications

---

## Role

You are a UI/UX designer and frontend developer responsible for improving student-facing system notifications and correcting notification-message logic.

---

## Description

Replace the standard chat-bubble presentation used for educator-issued exemptions and special-access notifications with visually distinct alert components. Use the KTUI light alert designs at the provided reference link as the design basis. Exemption notifications must use the destructive alert style, while special-access notifications must use the success alert style. Also correct the message-generation logic so exemption messages do not repeat the assessment name, reason label, or reason text.

---

## Primary Objective

Present exemption and special-access messages as KTUI-style alerts while eliminating duplicated or redundant notification content.

---

## Secondary Objectives

* Use a destructive alert for exemption notifications.
* Use a success alert for special-access notifications.
* Preserve the intended notification details while making the message concise and readable.
* Correct the underlying message construction that sometimes repeats the exemption statement and reason.

---

## Success Criteria

* Exemption notifications are displayed as destructive KTUI light alerts instead of normal chat bubbles.
* Special-access notifications are displayed as success KTUI light alerts instead of normal chat bubbles.
* Each notification displays its message only once.
* The assessment name appears only once in the notification.
* The `Reason:` label and the educator-provided reason appear only once.
* A corrected exemption notification follows a clear structure such as: `You have been exempted from Quiz #1. Reason: You're absent from our class, and I will not provide another opportunity to take it regardless of the reason.`
* The alert design is based on the KTUI light alert reference: `https://ktui.io/docs/alert#light`.

---

## Context & Dependencies

* The current student notification interface displays educator-issued exemptions and special access as standard chat bubbles.
* The implementation should use the KTUI light alert component or follow its documented design pattern.
* Notification content is generated when an educator exempts a student from an assessment or grants the student special access.
* The current exemption-message logic can concatenate already formatted content with the same message again, causing duplication.

---

## Stakeholders

* **Students:** Receive and read exemption or special-access notifications.
* **Educators:** Issue exemptions and grant special access.
* **Frontend developers:** Implement the KTUI alert presentation.
* **Application developers:** Correct the notification-message generation logic.

## Detailed Breakdown

### Exemption Notifications

When an educator exempts a student from an assessment, display the notification using the KTUI light destructive alert style. The alert must clearly communicate that the student has been exempted, identify the relevant assessment, and display the educator’s reason once when one is provided. The exemption notification must no longer appear as an ordinary chat bubble.

### Special-Access Notifications

When an educator grants a student special access, display the notification using the KTUI light success alert style. The message should clearly identify the granted access and any relevant assessment information without duplicating content. The special-access notification must also replace the current ordinary chat-bubble presentation.

### Duplicate-Message Correction

Correct cases where the exemption notification is repeated inside the reason or appended to another copy of itself. For example, the application must not produce content such as:

`You have been exempted from assessment Quiz #1. Reason: You have been exempted from assessment Quiz #1. Reason: You're absent on our class, I won't give any chance to take this regardless of your reason.`

The final output should contain one exemption statement followed by one reason label and one educator-provided reason. Ensure the fix addresses the message-construction logic rather than merely hiding duplicated text in the interface.
